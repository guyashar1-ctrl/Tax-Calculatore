## 2. הגנות הבטיחות שנוספו

1. **שער בפני כתיבה לפרודקשן.** כל סקריפט של הסביבה עובר דרך `scripts/staging-lib.mjs`.
   מזהה הפרודקשן כתוב שם במפורש, וכל ניסיון כתיבה אליו **עוצר את הסקריפט**.
   קריאה מהפרודקשן אפשרית רק דרך `readProd`, שמסומנת במפורש כקריאה בלבד.
2. **המידע האישי מסונן במקור.** `staging-clone.mjs` בונה את השאילתה כך שעמודות
   המידע האישי **אינן נבחרות בכלל** בפרודקשן. הן לא עוברות ברשת ולא נשמרות בזיכרון.
3. **שער אימות אחרי כל העתקה.** הסקריפט נופל אם נמצא ולו מייל אחד שאינו
   `delivered@resend.dev`, חתימה אחת, מסמך אחד או מייל אחד ביומן.
4. **אפס משימות מתוזמנות.** נבדק אחרי כל שינוי ב-`staging-verify-schema.mjs`.
   שום דבר בסביבה לא יוצא מעצמו.
5. **טוקנים ציבוריים חדשים.** כל טוקן נוצר מחדש באקראי. נבדק בהשוואת גיבובים:
   **אפס חפיפה** בין 14 הטוקנים בפרודקשן ל-28 שבסביבת הבדיקות. קישור מהפרודקשן
   לא ייפתח כאן, וקישור מכאן לא ייפתח שם.
6. **סודות נפרדים.** משתמש, סיסמה ומפתחות של הסביבה נוצרו בה עצמה.
   **לא הועתק שום מפתח, סוד או הגדרה מהפרודקשן.**
7. **פרופיל משרד בדיוני.** גם הפרטים של גיא אינם בסביבה — המשרד הוא
   "משרד בדיקות PIVO".

## 4. איך מריצים את האפליקציה מול הסביבה

```bash
npm run dev:staging
```

הפקודה מריצה `vite --mode staging`, שקורא את `.env.staging`.
**לפני כל בדיקה** יש לוודא שהמסך מחובר לסביבה הנכונה — ראה סעיף 5.

## 5. בדיקת "לאיזה מסד אני מחובר"

```bash
npm run staging:check
```

מדפיס לאיזה פרויקט מצביע כל קובץ סביבה, ונופל אם `.env.staging` מצביע לפרודקשן.
בדפדפן אפשר לוודא בכל רגע דרך לשונית הרשת: הבקשות חייבות לצאת אל
`evdfxjqrkgugssfrdoxd.supabase.co`. אם מופיע `uoweoqtuiettozagwgdw` — **לעצור מיד**.
