## 1. המסע המוצע ונקודות הכניסה

### 1.1 העיקרון
- **ידע** = מה הכלל ולמה. בית אחד: «ידע מס» בסרגל הראשי (היום בתפריט האווטאר).
- **שנת מס של לקוח** = מה ידוע, מה חסר, אילו ראיות, מה הוחלט. **אין לשונית «שנת מס»** (תוקן 11.10.2026 לפי ההדמיה המאושרת): כרטיסי שנה ב«תיק מס › שנות מס», ודף התהליך (נפתח מ«בקשות») מציג את תמונת השנה. ראו `stage2-execution-plan.md` §6.
- **תהליך** (הערכת מס, דוח שנתי, הצהרת הון) = **בקשה** ב«בקשות», עם דלת לשנת המס כמשטח פירוט.
- **עובדה מתמשכת** (מצב משפחתי, תיקים, ייצוג) נשארת ב«תיק מס». **סכום שנתי** עובר לשנת המס.

### 1.2 איפה כל יכולת נמצאת

| יכולת | איפה מוצאים אותה | מאיפה עוד מגיעים | מי פועל |
|---|---|---|---|
| ללמוד נושא | ידע מס › נושא (מסלול 7 חלקים) | «למה?» בכל כרטיס בשנת המס; חיפוש | רו״ח, עובד |
| לראות על מי נושא חל | בתחתית הנושא: «לקוחות שהנושא נוגע להם» | — | רו״ח |
| הערכת מס לשנה | בקשות › «הערכת מס 2026» → שנת מס | עונת המס; «הצעד הבא» בבקשות | המשרד |
| לשאול את הלקוח מה חסר | שנת מס › «מה חסר» › «הכן שאלות» | — | המשרד יוצר, הלקוח עונה בדף האישי |
| לייבא ראיה (פייפרלס, צילום 134, אישור קופה) | שנת מס › «השנה לפי תקופות» › ייבוא | מסמכים › תיקיית השנה | המשרד |
| לקרוא 134 / ESNA | שנת מס › «קרא שוב 134» / «קרא ESNA» | אוטומציות (תזמון) | העובד האוטומטי, בהפעלת המשרד |
| ליישב סתירה | שנת מס › «סתירה ליישוב» | «הצעד הבא» | רו״ח |
| לאשר הערכה | שנת מס › «שמור תמונת מצב לאישור» | — | רו״ח |
| דוח שנתי | בקשות › «דוח שנתי 2025» → שנת מס 2025 › «דוח שנתי» | עונת המס | לקוח (מסמכים), רו״ח (כיסוי, פלט) |
| הצהרת הון ראשונה | בקשות › «הצהרת הון ליום X» → שנת מס › «הצהרת הון» | מסמכים (מכתב הדרישה) | רו״ח, לקוח |
| עבודת מס (כל המשרד) | סרגל ראשי › «עבודת מס» | — | רו״ח |
| בדיקת עדכניות הידע | ידע מס › «עדכניות» (לכל כלל, לא לכל מאגר) | משימה רבעונית קיימת | רו״ח + פרומפט התחזוקה |

«שנת מס ›» בטבלה = תמונת השנה בדף התהליך (נפתח מבקשות או מכרטיס השנה ב«תיק מס»), לא לשונית; «הכן שאלות» = «הוסף לבקשה «השלמת מידע»» בכרטיס «עכשיו». הצהרת הון — לפי יום קובע, מחוץ לשנת המס (תוקן 11.10.2026).

### 1.3 מה הלקוח רואה
- בדף האישי: פריטי «השלמת מידע» (שאלות ומסמכים) עם הסבר קצר למה שואלים, בלי מונחי מס ובלי קודי טופס.
- אחרי אישור הערכה: סיכום ללקוח (טיוטה שהמשרד מאשר ושולח בנפרד). **אין שליחה אוטומטית.**
- בהצהרת הון: רשימת נכסים/התחייבויות ליום הקובע, לפי אדם, עם העלאת אסמכתאות.

## 2. יסודות «בקשות» — בדיקה מפורשת

**המלצה: לשמור את כל היסודות כפי שהם. אין הצעה להחליף אף אחד מהם.**

| יסוד | איך הוא חל כאן |
|---|---|
| כל עבודה משמעותית = שורה ב«בקשות» | שלושה סוגי בקשה חדשים: `tax_estimate`, `annual_return`, `wealth_declaration`. משטח הפירוט = שנת המס |
| אין פירוט בלי שורה | הדוח השנתי היום **מפר** את זה (סשן בלי בקשה). תיקון בשלב 2: כל סשן קיים מקבל בקשה |
| יחידת עבודה אחת = מחזור אחד | זהות: בעלים + סוג + שנת מס (או יום קובע להצהרת הון) + פתוח. אידמפוטנטיות בשרת |
| בעלים ≠ נושא | הבעלים = הכרטיס; הנושא = `client` / `spouse` / שניהם. עובדות וראיות שומרות את התפקיד |
| בקשה שהושלמה היא היסטוריה | הערכה מאושרת לא נפתחת מחדש. עדכון = גרסה חדשה של הערכה בתוך הבקשה הפתוחה, או בקשה חדשה אחרי סגירה |
| תקשורת שייכת לפריט שגרם לה | שאלות ללקוח = בקשת־בת `info_collection` (סוג חדש — לא קיים היום; התשובות נכתבות כעובדות ממתינות, לא ל-payload ולא לכרטיס) תחת הבקשה; המייל נשלח רק ב«שלח בקשות» הקיים |
| המסך לא טוען «נשלח/הושלם» בלי ראיה | «נקרא מ-134» רק עם שורת קריאה מוצלחת; כשל קריאה מוצג ככשל |
| תנאי־קדם נגזרים בשרת | «אי אפשר לאשר הערכה לפני הכרעת סתירות ותחזית» = מצב נגזר של הבקשה, לא `if` במסך |
| משטח מקצועי מתאר מצב | שנת המס מתארת ומציעה פעולה; כל עבודה שהיא פותחת הופכת לבקשה או לפריט בבקשה |

«עבודת מס» היא **תצוגת משרד מסוננת של בקשות קיימות**, לא רשימה חדשה ולא משימות.

## 3. כללים וידע — מרשם אחד לכל הצרכנים

### 3.1 החלטה: מרשם בקוד, לא פלטפורמה במסד
הכללים משתנים לכל היותר כמה פעמים בשנה, וכל שינוי צריך ביקורת, בדיקות ופריסה. לכן המרשם נשאר **קובץ TypeScript בגרסה** (כמו היום), עם מבנה חדש. במסד נשמר רק **מזהה גרסת המרשם** שעליו נשענה הערכה מאושרת. אין עורך כללים במסך בשלב הזה.

```ts
// src/features/taxRules/types.ts
type Basis = 'primary' | 'secondary' | 'derived' | 'unverified';
interface RuleValue {
  taxYear: number;                 // או effectiveFrom/To לכלל שאינו שנתי
  effectiveFrom?: string; effectiveTo?: string;
  value: number | string | Record<string, number>;
  basis: Basis;
  sourceId: string;                // → SOURCES
  locator?: string;                // «מדריך 2025, סעיף 51–52»
  checkedAt: string;               // מתי נבדק בפועל
  note?: string;
}
interface Rule {
  id: string;                      // 'sf.se.ceiling'
  label: string; unit: '₪' | '%' | 'rule' | 'date';
  law?: string;                    // 'סעיף 17(5א)'
  values: RuleValue[];             // היסטוריה מלאה — לא מוחקים שנים
  computable: boolean;             // false = הסבר מקצועי בלבד, לא נכנס לחישוב
}
```

- `rule(id, year)` מחזיר ערך לשנה; אם אין ערך לשנה המבוקשת — מחזיר את השנה הקרובה **עם סימון** «אין ערך ל-2026», לא בשקט.
- **ביסוס חלש מתפשט:** נושא ידע, שאלה או חישוב מציגים את הביסוס החלש ביותר מבין הכללים שהם משתמשים בהם. אין תג «אומת» לכל המאגר.
- `RULESET_VERSION` = hash של תוכן המרשם, נשמר בכל הערכה מאושרת.

### 3.2 נושאי ידע
```ts
interface KnowledgeTopic {
  id: string; title: string; area: 'savings' | 'business' | 'family' | 'reporting' | 'wealth' | ...;
  form1301: { section: string; fields: string[] }[];   // «בטופס» (מחלופה א׳)
  sections: { meaning; whoApplies; example; combinedCase; exceptions; inTheFile; deepDive };
  ruleIds: string[];                                    // הערכים בטקסט נשלפים מכאן: {{rule:sf.se.ceiling}}
  intakeQuestionIds: string[];                          // «בשאלון»
  appliesTo?: (facts) => 'yes' | 'no' | 'unknown';      // «לקוחות שהנושא נוגע להם»
  claims?: { text; verdict: 'confirmed' | 'partial' | 'unverified' | 'rejected'; why }[];
  media?: { kind: 'video' | 'link'; url; title; checkedAt; captions: boolean }[];
}
```
מספר לעולם לא נכתב כטקסט חופשי בנושא — רק דרך `{{rule:id}}`. זה מה שמאפשר לעדכון כלל להגיע לכל מקום.

### 3.3 צרכנים והשפעה
סקריפט `npm run rules:impact -- <ruleId>` מחפש שימושים במרשם (נושאים, שאלות, חישובים, מיפוי 1301) ומדפיס רשימה. בדיקת יחידה נכשלת אם כלל מוזכר בקוד ואינו במרשם, או אם `computable:false` משמש בחישוב.

## 4. עובדות, ראיות והערכות — מבנה הנתונים

### 4.1 עובדות שנתיות
```sql
create table tax_year_facts (
  id uuid primary key, user_id uuid not null, client_id uuid not null,
  subject_role text not null check (subject_role in ('client','spouse','business','household')),
  tax_year int not null, period_from date, period_to date,
  key text not null,                         -- allowlist בשרת, כמו GOVERNED_FACT_KEYS
  value jsonb not null,
  basis text not null check (basis in ('actual','forecast','final','declared','derived')),
  source text not null,                      -- questionnaire | manual | import | automation | institution_alignment
  evidence_id uuid references tax_evidence(id),
  status text not null default 'pending' check (status in ('pending','accepted','rejected','superseded')),
  decided_by uuid, decided_at timestamptz, supersedes uuid, note text,
  created_at timestamptz default now()
);
```
- **ריק ≠ אפס:** ערך ריק לא נשמר כעובדה. «לא ידוע» = אין שורה מאושרת.
- **תחזית ≠ בפועל:** `basis='forecast'` לעולם לא מחליף `actual`; שניהם נשמרים.
- כתיבה רק דרך RPC עם allowlist ובדיקת `stale_conflict` (אותו דפוס של `accept_tax_fact_change`).

### 4.5 הצהרת הון
**שני דברים נפרדים (תוקן 10.10.2026 — הנוסח הקודם סתר את עצמו וקבע חסימה שלא אושרה):**
1. **הכנה** — עבודה על רשימת נכסים והתחייבויות ליום קובע. אפשר לפתוח אותה **בכל עת**: כשהגיע מכתב, כשמצפים לדרישה (למשל אחרי פתיחת עסק), או כהכנה יזומה. היא מוצגת «הכנה · אין דרישה מתועדת» כל עוד אין ראיה. אין חסימה.
2. **דרישה רשמית ומועד מחייב** — המערכת **אומרת** «יש דרישה» ומציגה **מועד הגשה** רק כשיש ראיה (מכתב הדרישה, או רישום ברשות שנקרא ונשמר) והמשרד אישר אותה. בלי ראיה: אין מועד מחייב; אפשר לרשום «יעד פנימי» שמוצג כך ולא כמועד רשות.

סטטוס מס, סוג תיק או ותק לבדם **לא** יוצרים «יש דרישה» ולא מועד. השדות הקיימים `capitalDeclarationRequired/Deadline` יוצגו «דווח, לא מתועד» עד שתצורף ראיה.

**בסיס רשמי:** בהנחיות טופס 1219 נכתב שממלאים את הטופס לפי דרישת פקיד השומה (סעיף 135(1)), ומגישים תוך 120 יום מהדרישה או מהמועד שההצהרה מתייחסת אליו; דף השירות: המאוחר מביניהם. לכן **הגשה** בלי דרישה מתועדת מקבלת אזהרה בולטת.
**החלטה עסקית פתוחה (גיא):** האם להגשה בלי דרישה מתועדת מספיקה אזהרה, או שהיא דורשת אישור מפורש של רו״ח? המלצה: אישור מפורש של רו״ח עם הערה, בלי חסימה טכנית.

```sql
create table wealth_declarations (
  id uuid primary key, client_id uuid not null, request_id uuid not null,
  sequence int not null default 1, previous_declaration_id uuid references wealth_declarations(id),
  as_of date not null,
  demand_status text not null default 'none'
    check (demand_status in ('none','reported_unverified','documented')),  -- רק 'documented' = «יש דרישה»
  demand_evidence_id uuid references tax_evidence(id), demand_date date,
  confirmed_by uuid, confirmed_at timestamptz,                               -- מי אישר שהראיה היא דרישה
  deadline date,            -- נגזר בשרת רק כש-demand_status='documented': greatest(demand_date, as_of) + 120
  internal_target date,     -- יעד משרד; לעולם לא מוצג כמועד רשות
  status text not null,     -- preparing | collecting | review | submitted
  submitted_evidence_id uuid, submitted_without_documented_demand boolean default false
);
create table wealth_items (
  id uuid primary key, declaration_id uuid references wealth_declarations(id),
  asset_key text not null,                         -- זהות יציבה בין הצהרות
  subject text check (subject in ('client','spouse','child')), child_ref text,
  part text check (part in ('A','B','C','D')),      -- חלקי טופס 1219
  form_field text,                                  -- 10…120, 130/140, 300…460, 500…760 לפי 1219
  category text, description text,
  cost_ils numeric, amount_fx numeric, currency text, fx_date date,
  basis text not null default 'cost',               -- 1219: עלות בפועל, לא שווי
  acquired_via text,                                -- purchase | inheritance | gift (ירושה/מתנה נרשמות 1 ₪)
  share_pct numeric, acquired_at date, evidence_id uuid
);
```
כללי הרישום מהנחיות 1219 שיחולו כבקרות: עלות ולא שווי; עלויות נלוות ושיפורים נוספים לעלות; ירושה או מתנה = 1 ₪; נכס בתשלומים = מחיר מלא והחוב בנפרד; מט״ח לפי השער היציג ביום התשלום; אין קיזוז בין חייבים לזכאים; חלק יחסי בנכס משותף; שקלים שלמים; שדה ריק = 0 בטופס (במערכת: «אין» הוא תשובה, לא ערך ריק).

**הצהרות במועדים שונים והשוואת הון (תוספת 10.10.2026).** המבנה תומך בהצהרה שנייה ואילך ובהשוואה בין שתיים:
- `sequence` ו-`previous_declaration_id`; בטופס 1219 החדש יש שדה «הון נטו שהוצהר בהצהרת הון קודמת» (חלק ד׳ 4), ולכן ההצהרה הקודמת היא נתון בטופס עצמו.
- `asset_key` יציב לכל פריט, להשוואה פריט מול פריט.
- בסיס השווי על הפריט, כדי שהשוואה לא תערבב עלות ושווי.

```sql
create table wealth_comparisons (
  id uuid primary key, client_id uuid not null, request_id uuid,
  from_declaration_id uuid references wealth_declarations(id),
  to_declaration_id uuid references wealth_declarations(id),
  net_worth_change numeric,          -- נגזר משני ההון הנקי
  explained jsonb,                   -- מקורות לפי שנה: הכנסה לאחר מס מתוך עובדות שנת המס/שומות, תקבולים פטורים, מתנות וירושות, הלוואות
  uses jsonb,                        -- הוצאות מחיה (הנחת משרד או שאלון), הוצאות חריגות
  unexplained numeric,               -- הפער שנותר
  status text, note text, decided_by uuid, decided_at timestamptz
);
```
ההשוואה **קוראת** עובדות שנתיות (פרק 4.1) ולא מעתיקה אותן, כך שהכנסה שכבר אושרה בשנת מס לא נכתבת שוב.
**מה כבר ידוע ממקורות:** המערכת המקוונת של הרשות מאפשרת לצרף «מסמכים המכילים הסברים לגידול הון» (הודעת 05.05.2025, רשמי). לפי סיכומי פסיקה (משני): משהרשות מצביעה על גידול הון, הנטל להסביר אותו בראיות עובר לנישום; בהיעדר נתונים הרשות נשענת על טבלאות הוצאות מחיה; טענה לעזרה מקרובים נבחנת בנטל מוגבר. לכן ההשוואה צריכה להציג לכל רכיב הסבר **את הראיה שלו**, ולהבחין בין «מוסבר בראיה», «מוסבר בטענה» ו«לא מוסבר».
**סדר העבודה:** המחקר הרשמי נמשך עכשיו בלי לחכות. החומרים של גיא (צילומים מקורס וקצות חוט) ישמשו להעמקה ולהשלמת פערים. **הכיסוי, השאלונים, נוסחי הפנייה ותבניות המשרד בתחום ההון ייסגרו רק אחרי סקירתם.**

### 4.6 מעבר מהמצב הקיים בלי לאבד עובדות
1. **הוספה, לא החלפה.** הטבלאות החדשות נוספות; השדות על `Client` נשארים ונקראים.
2. **העתקה:** לכל סכום שנתי קיים על הכרטיס נוצרת שורת `tax_year_facts` עם `basis='declared'`, `status='pending'` ו«שנה מוצעת» שהמשרד מאשר (`field_meta.syncedAt` הוא מועד כתיבה, לא שנת מס — תוקן 11.10.2026). שום ערך לא נמחק.
3. **הכרעה:** בשנת המס מופיע «מידע שעבר מהכרטיס — לאשר שנה». עד האישור הוא לא נכנס לחישוב.
4. **מעבר קוראים:** מסכים וחישובים קוראים משנת המס; השדה על הכרטיס הופך להיטל לקריאה בלבד (טריגר), ואחר כך יוצא מה-allowlist.
5. **הדוח השנתי:** לכל `annual_report_session` פתוח נוצרת בקשה `annual_return` (אידמפוטנטית); התשובות נשארות במקומן.
6. **הצהרת הון:** `capitalDeclarationRequired/Deadline` לא נמחקים. אם יש מכתב דרישה במסמכים — נוצרת בקשה עם `demand_status='documented'` אחרי אישור המשרד. אם אין — הם מוצגים «דווח, לא מתועד — לצרף ראיה», והמשרד יכול לפתוח הכנה בלי מועד מחייב.
7. **134:** הקריאה הקיימת של ראש התיק נשמרת; טבלת התקופות היא תוספת לאותה פעולה, לא פעולה שנייה.

## 5. ייבוא פייפרלס, 134 ו-ESNA

### 5.1 פייפרלס — ידני קודם
- **קלט:** רו״ה כפי שהופק (PDF). אם פייפרלס מאפשר ייצוא Excel/CSV — עדיף, כי חילוץ מ-PDF שביר.
- **זרימה:** העלאה → שמירת המקור במסמכים › שנת המס → בדיקת זהות (שם העסק / ע.מ. בכותרת מול הכרטיס) → חילוץ חודשים → **המשרד בוחר «סגור עד»** → חודש ריק אחרי הסגירה = פתוח; חודש ריק לפני הסגירה = «לבדוק» → אישור → עובדות `actual` לפי חודש.
- **בסיס:** «לפני תיאומי מס» (אושר ע״י גיא). התיאומים נרשמים ב-`adjustments` של ההערכה עם הפניה לקטגוריה בספרים, ולכן אי אפשר לתאם את אותה קטגוריה פעמיים.
- **כפילויות:** ייבוא נוסף לאותה שנה יוצר ראיה חדשה; השוואה לקודמת מציגה מה השתנה (עדכון ספרים), ולא דורס בשקט.
- **אוטומציה בעתיד** תכתוב לאותה `tax_evidence` עם `captured_by='worker:…'` — אותו מסך בדיקה.
- **דוגמאות נוספות שיידרשו מגיא** (רק בתחילת שלב 3, ולמטרה מוגדרת):
  1. רו״ה של **שנה סגורה** (2025) — כדי להשוות סיכומים לנספח א׳ (1320) ולבדוק שהקטגוריות ממופות לשורות הנספח.
  2. **כרטיס חשבון של הוצאות רכב** באותה שנה — כדי לוודא שאין בפייפרלס כבר תיאום חלק פרטי (מניעת תיאום כפול).
  3. **ייצוא Excel** של אותו רו״ה, אם קיים בפייפרלס.

### 5.2 134 — טבלת התקופות
- הרחבת `shaamSyncIncomeTaxFile` (או handler מקביל באותה פעולה): קריאת שורות הטבלה (תקופה, מצב דיווח, מחזור, חיוב, תשלומים, ניכוי במקור, תאריך עדכון) ושורת «תשלומי מקדמות ללא ייעוד», + צילום מסך כראיה.

- **מקורות העוגנים:** לבנות מקוד המסך החי ומההקלטה; לבדוק על staging/לקוח בדיקה. אין ניחוש עוגנים.
- תיקון ההערה המיושנת «ארבעה שדות».

### 5.3 ESNA
- קורא חדש: גבייה מע״מ › פרטי עוסק › «סיכומי דיווח ESNA» לשנה נבחרת. אותו מודל `authority_period_readings` עם `authority='vat'`.
- שנה בלי דיווחים (כמו 2026 בהקלטה) ≠ אפס: `report_state` לפי מה שמוצג, או `unknown`.
- קריאה בלבד. אין דיווח, אין תיקון.

## 7. תחזוקת ידע — פרסום, שחזור ושאלות פתוחות

- **שינוי כלל** = שינוי בקובץ המרשם + בדיקות + ביקורת diff + פריסה. אין עדכון ישיר במסד.
- **שינוי מקור** (קישור, ניסוח) ≠ **שינוי ערך/דין**. שינוי מקור לא משנה `checkedAt` של הערך; שינוי ערך מוסיף `RuleValue` חדש ולא מוחק את הקודם.
- **בדיקה חלקית או שנכשלה** משאירה את הביסוס הקודם ומוסיפה `note` — לעולם לא משדרגת ל-●.
- **שחזור:** revert של קומיט הכלל. הערכות שאושרו בזמן הגרסה השגויה מסומנות «כלל השתנה» ולא מחושבות מחדש.
- **הפרומפט:** `recurring-knowledge-update-prompt.md`.
