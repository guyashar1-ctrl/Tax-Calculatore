## 0. בשורה אחת

הלקוח לא ממלא טופס. המשרד פותח בקשה («הערכת מס 2026» או «דוח שנתי 2025»), והמערכת מרכיבה **תמונת שנה** מכמה מקורות:
- מה שכבר ידוע בתיק;
- מה שאושר בשנה הקודמת;
- מסמכים וקריאות מהרשויות.

מתוך התמונה המערכת מציעה למשרד רק את מה שחסר ורלוונטי. הלקוח מקבל בדף האישי:
- כמה שאלות פתיחה לפי תחומי חיים;
- פירוט רק אחרי «כן»;
- רשימת מסמכים.

כל תשובה נשמרת כעובדה לשנה, לאדם ולתקופה, עם מקור, ונכנסת לשימוש רק אחרי אישור המשרד. 305 שדות 1301 ו-131 פריטי המידע של הנספחים רצים מאחור, כבקרת כיסוי בלבד.

## 1. מה משותף לשאלון הערכת המס ולשאלון הדוח השנתי, ומה ייחודי

### 1.2 מה ייחודי

**הערכת מס בלבד** (הנתונים נשמרים כבר עכשיו, החישוב בשלב 3):
- **חודש החתך.** תאריך ההערכה, מועד תחילת השינוי במקדמה ותאריך בדיקת היתרות — ארבעה שדות נפרדים.
- **נתוני אמת לפי חודש עד החתך**, ותחזית נפרדת לחודשים שאחריו: תחזית לקוח ותחזית משרד, כל אחת עם הנחה ומקור.
- **אירועים חד־פעמיים**, מסומנים כך שלא יוכפלו בקצב שנתי.
- **מסמכי ביניים:** תלוש מצטבר במקום 106, ורו״ה עד החתך במקום רו״ה שנתי.
- **מקדמות:** השיעורים הנוכחיים והיתרות ברשויות.

**דוח שנתי בלבד:**
- **מסמכים סופיים:** 106, 867, אישורים שנתיים מהקופות, קבלות.
- **פרטי נספחים:**
  - נכס: גוש, חלקה, תחילת השכרה;
  - עסקאות הון;
  - רישום רכוש קבוע;
  - יתרות להעברה לשנה הבאה.
- **שדות להגשה בלבד**, לפי ההחלטה «נתון של טופס אחד נשאל בהגשה»: חשבון להחזר, הצהרות, תיבות סימון נדירות.
- **בקרת כיסוי 1301:** בדף הדוח, כסעיף מקופל.

### 1.3 כשהשנה עוברת מהערכה לדוח

בקשת «דוח שנתי 2025» קוראת את מה שאושר ב«הערכת מס 2025»:
- **שאלות פתיחה שאושרו** (למשל «יש שכר דירה — כן») לא נשאלות שוב. הלקוח רואה אותן ברשימת «זה מה שידוע לנו — עדיין נכון?».
- **סכום שהיה תחזית או נכון עד החתך** מקבל את הסטטוס «ידוע, חסרה אסמכתה סופית». מבקשים את המסמך, לא את השאלה.
- **ההערכה המאושרת לא משתנה.** העובדות הסופיות נשמרות לצד התחזית ולא דורסות אותה.

### 2.1 שימוש במה שכבר קיים — בלי לשאול שוב

**1. עובדות מתמשכות בכרטיס** (משפחה, ילדים, יישוב, תואר, מעבידים, עסקים, נכסים, חשבונות):
- משמשות לשני דברים: לקבוע מה רלוונטי, ולמלא מראש.
- הלקוח מתבקש **לאשר** («2 ילדים: דנה 2014, יואב 2019 — נכון?»), לא לענות מחדש.
- אישור שלא שינה דבר נרשם כעובדת שנה; הכרטיס לא נכתב.

**2. סכומים שנתיים שיושבים היום על הכרטיס** — כ-17 שדות, ועוד סכומים בתוך מעבידים, עסקים, חשבונות, ילדים ובן/בת זוג:
- כל ערך מועתק לשנת המס כעובדה במצב «לאשר שנה». שום ערך לא נמחק.
- ‼ אין לשדות האלה שנה, ו-`field_meta.syncedAt` הוא מועד כתיבה, לא שנת מס. לכן המערכת **מציעה** שנה, והמשרד מאשר.
- עד האישור הערך לא נכנס לחישוב ולא נחשב «ידוע».
- הסעיף הזה מתקן את פרק 4.6 בתוכנית הארכיטקטורה, שהסיק שנה מ-`field_meta`.

**3. שאלוני הדוח השנתי הקיימים** (`annual_report_sessions` / `annual_report_answers`):
- **לכל סשן יש שנת מס.** לכן התשובות עוברות לעובדות לאותה שנה — במצב «ממתין לאישור», לא «אושר».
- לכל סשן פתוח נוצרת בקשה «דוח שנתי <שנה>», פעם אחת בלבד, והתשובות נשארות במקומן.

**4. מסמכים קיימים עם שנה** (`documents.year`) מוצגים כראיה מוצעת לפריט המתאים. השיוך דורש לחיצה של המשרד.

**5. קריאות מהרשויות** (ראש תיק 134, הכנסות מב״ל): מוצגות כראיה עם מועד הקריאה. כשל בקריאה מוצג ככשל, לא כ«אין».

**6. «בנק השאלות» של השאלון הקיים:**
- הניסוח, ההבחנה קבוע/שנתי והבעלות (רשום / בן־זוג / שניהם) עוברים לתחומים.
- ‼ **מסך הסנכרון של השאלון הקיים כותב תשובות שנתיות ישר לכרטיס. בשלב 2 זה משתנה:**
  - תשובה שנתית → שנת המס;
  - תשובה מתמשכת → עובדה מבוקרת ממתינה.

## 3. איך נשמרים שנת המס, האדם, התקופה, המקור ומצב האישור

### 3.1 עובדה לשנה

החלפה לטיוטת פרק 4.1 — שינויי שמות והרחבות לפי הקוד הקיים.

```sql
create table tax_year_facts (
  id uuid primary key, user_id uuid not null, client_id uuid not null,
  tax_year int not null,
  item_key text not null,            -- פריט מידע מהקטלוג (allowlist בשרת, כמו GOVERNED_FACT_KEYS)
  subject_role text not null check (subject_role in ('client','spouse','couple')),
  entity_kind text check (entity_kind in ('employer','business','property','account','foreign_source','fund','child','transaction','company')),
  entity_ref text,                   -- id של הפריט ברשימה בכרטיס (לכולם כבר יש id יציב), או מזהה עסקה
  period_kind text not null check (period_kind in ('year','months','as_of','transaction','carry_forward')),
  period_from date, period_to date,  -- months: ינואר..החתך; as_of / transaction: תאריך אחד
  answer_state text not null check (answer_state in ('value','zero','no','not_applicable')),  -- «חסר» = אין שורה
  value jsonb,                       -- ריק רק כש-answer_state ≠ 'value'
  basis text not null check (basis in ('actual','actual_to_date','forecast','final','declared','derived')),
  forecast_by text check (forecast_by in ('client','office')), assumption text,
  is_one_off boolean not null default false,
  source text not null check (source in ('portal','office','document','import','automation','card_migration','legacy_questionnaire')),
  request_id uuid,                   -- הבקשה שבה נאסף (תקשורת שייכת לפריט שגרם לה)
  evidence_id uuid references tax_evidence(id),
  status text not null default 'pending' check (status in ('pending','accepted','rejected','superseded')),
  decided_by uuid, decided_at timestamptz, supersedes uuid references tax_year_facts(id), note text,
  created_at timestamptz not null default now()
);
-- עובדה אחת מאושרת לזהות: (client, year, item, subject, entity, period, basis). חדשה ⇒ הקודמת superseded.
```

**החלטות שנכנסות למבנה:**
- **שנת מס** — עמודה, ולא נגזרת מתאריך הכתיבה.
- **האדם** — תפקיד, לא זהות:
  - `client` או `spouse`, כמו `subjectRole` בבקשות.
  - `couple` לעובדה של משק הבית, כמו מצב משפחתי בסוף השנה.
  - עסק, נכס או חשבון אינם «אדם». הם `entity_kind` + `entity_ref`, והבעלות עליהם נקבעת בכרטיס (פער 2).
  - המבנה הזה מתקן את הטיוטה שהכניסה `business` ו-`household` לשדה האדם.
- **תקופה:** שנה; חודשים (עד החתך); יום קובע; תאריך עסקה; יתרה להעברה.
- **ריק ≠ אפס:**
  - «חסר» = אין שורה.
  - «אפס», «לא» ו«לא חל» הם תשובות שנשמרות.
  - זה מאמץ את `AnswerState` שקיים היום כטיפוס בלבד.
- **בסיס:** תחזית לעולם לא מחליפה «בפועל». שתיהן נשמרות זו לצד זו. «עד החתך» ו«סופי» נפרדים.
- **מקור:**
  - מאיפה הגיע הנתון: דף אישי, משרד, מסמך, ייבוא, אוטומציה, מעבר מהכרטיס, שאלון ישן.
  - באיזו בקשה הוא נאסף.
  - איזו ראיה תומכת בו.

### 3.2 מצב אישור

- **`pending`** — הגיע ועוד לא נבדק. מוצג למשרד, לא נכנס לחישוב.
- **`accepted`** — אושר: מי אישר ומתי.
  - אם המשרד מתקן תשובה של לקוח, נוצרת שורה חדשה (מקור: משרד) שמחליפה את הקודמת. התשובה המקורית נשמרת כהיסטוריה.
- **`rejected`** — נדחה עם הערה. אפשר לבקש שוב מהלקוח; זה פריט חדש, לא כתיבה מחדש.
- **`superseded`** — הוחלף בעובדה חדשה יותר.
  - הערכה מאושרת (שלב 3) שומרת את מזהי העובדות שעליהן נשענה, ולכן גם עובדה שהוחלפה ממשיכה להצביע עליה.

**אכיפה בשרת:**
- **ממשק כתיבה אחד:** כתיבה רק דרך RPC עם allowlist של `item_key`. אותו דפוס של `_tax_fact_field_op`, כולל `stale_conflict` כשהעובדה השתנתה בזמן העיון.
- **שתי רשימות זהות:** הרשימה בשרת זהה לקטלוג ב-TS, ובדיקה אוטומטית נועלת את זה (כמו `GOVERNED_FACT_KEYS`).
- **מה המשרד מאשר ומה עובר מעצמו:** לפי ההמלצה בשאלה 2 בסעיף 8, אישור «ללא שינוי» של עובדה שכבר אושרה עובר מעצמו. ערך חדש תמיד ממתין לאישור.

### 3.3 ראיה

`tax_evidence` נבנית כמו בפרק 4.2, בשלב 2 בצורה מינימלית:
- מסמך מקורי, סוג, שנה, תקופה, אדם ומצב בדיקה;
- בדיקת זהות: השם או המספר במסמך מול הכרטיס.

**סוגי מסמך:** בשלב 2 מוסיפים סוגים כמו 106, 867, אישור קופה שנתי, רו״ה, קבלת תרומה, חוזה מכר ודוח פחת. הם נוספים כ-`label_id` במסמכים הקיימים, לא כמערכת קבצים חדשה. תיקיית שנה בתוך תיקיית הלקוח בנויה על `document_folders.year`, שכבר קיים.

**חילוץ אוטומטי** של סכומים מהמסמך — לא בשלב 2. המשרד מזין את הסכום מהמסמך, והעובדה מצביעה על הראיה.

## 4. כיצד הלקוח מוסר עובדות ומסמכים, והמשרד משלים ומאשר

### 4.1 הזרימה

1. **המשרד פותח בקשה:** בקשות › «＋ בקשה חדשה» › «הערכת מס לשנה» או «דוח שנתי», מתבנית ובלחיצה אחת.
   - פעם אחת לכל לקוח, סוג ושנה: לחיצה כפולה מחזירה את אותה בקשה, כי זהות הבקשה נאכפת בשרת.
   - הבקשה מוחזקת עד אישור הצעת המחיר, כמו כל בקשה, כשרלוונטי.
2. **דף התהליך מציג את תמונת השנה** (סעיף 5). כרטיס «עכשיו» אומר: «חסרים 7 פריטים — 5 מהלקוח, 2 מהמשרד».
3. **המשרד בוחר מה לשאול:** «הוסף לבקשה «השלמת מידע»» יוצר בקשת־בת `info_collection` תחת הבקשה.
   - כל פריט נושא `item_key`, אדם, ישות ותקופה.
   - פריט שהמשרד משלים בעצמו לא נשלח ללקוח.
4. **שליחה** דרך «שלח בקשות» הקיים: מייל אחד, עם קישור לדף האישי, לכתובת שבכרטיס. אין שליחה כתופעת לוואי של פעולה אחרת.
5. **הלקוח עונה בדף האישי.** כל תשובה ננעלת כ«נשלח למשרד» ונרשמת כעובדה ממתינה עם `source='portal'`.
   - אדם אחר במשק הבית (בן/בת זוג) מופיע בדף של הבעלים, עם נושא ברור בכותרת: «על מיכל: עבדה כשכירה?». אין לו דף משלו.
6. **המשרד מאשר.** כרטיס «לאשר את תשובות נועה» מציג כל שורה עם מקור ותאריך. הפעולות:
   - לאשר;
   - לאשר הכול;
   - לתקן (ערך משרד שמחליף את התשובה);
   - לדחות ולבקש שוב.
7. **סיום:** בקשת־הבת נסגרת כשכל פריטיה נענו או בוטלו. הבקשה הראשית ממשיכה (ראיות ותחזית בשלב 3, הכנת הדוח בשלב 4).

### 4.2 מה הלקוח רואה

תבנית ההדמיה המאושרת:
- **כרטיס לכל בקשה.** שאלה אחת למסך, עם «1 מתוך 6».
- **«למה שואלים?»** מקופל, בלשון פשוטה, בלי קודי טופס.
- **תשובות:** כן / לא / לא בטוח. פירוט נפתח רק אחרי «כן».
- **«לא בטוח»** הופך לפריט למשרד, לא לשאלה נוספת ללקוח.
- **מסך «זה מה שידוע לנו»** לפני השאלות החדשות: רשימת אישור קצרה, למשל:
  - «2 ילדים»;
  - «עובדת ב-X»;
  - «נכס מושכר ברחוב Y».
  
  לכל פריט — «נכון» או «השתנה». רק «השתנה» פותח שאלה.
- **מסמכים:** רשימה לפי תחום. «אין לי עדיין» נרשם כמצב, למשל «106 — יגיע בפברואר», ולא כחוסר תגובה.
- **שמירה וחזרה:** הלקוח יכול לעצור ולחזור. התשובות נשמרות בשרת, לא בדפדפן.

### 4.3 מנגנון בקוד

**יש היום:**
- `custom_request` עם `requirements[]` — התשובות נשמרות בתוך הבקשה;
- §16 — שכותב לכרטיס **מאושר מיד**.

שניהם לא מתאימים לעובדות לשנה, ולכן:
- **סוג בקשה חדש `info_collection`**, בת של `tax_estimate` / `annual_return`, עם ענף ב-`_portal_step_items`.
  - הוא מציג את הפריטים ברכיבי הקלט הקיימים: כן/לא, סכום, תאריך, בחירה, קובץ.
  - כל תשובה נכתבת ל-`tax_year_facts` במצב `pending`. ה-payload שומר רק הפניה לפריט ומצב «נענה».
- **§16 נשאר כמו שהוא**, לשדות קנוניים בכרטיס בלבד. «אי אפשר לאשר הערכה לפני הכרעת סתירות» (שלב 3) יוגדר כתנאי אישור של הבקשה, לא כתנאי־קדם של §16.
- **קבצים מהדף האישי** — דרך `portal-upload-document` הקיים, עם שנה ותווית לפי הפריט. הקובץ יוצר ראיה בבדיקה.

## 5. איך מבקשים רק מידע רלוונטי וחסר

### 5.1 מצב לכל פריט (פונקציה טהורה, נבדקת)

הפונקציה מקבלת את הכרטיס, את עובדות השנה ושל השנה הקודמת, את הראיות ואת הבקשות הפתוחות. לכל פריט מידע היא מחזירה אחד מהמצבים:

| מצב | פירוש | מה קורה |
|---|---|---|
| ידוע | עובדה מאושרת מתאימה לתכלית: בפועל או סופי לדוח; בפועל או תחזית להערכה | לא שואלים |
| ידוע, חסרה אסמכתה סופית | יש תחזית או «עד החתך», והתכלית היא דוח | מבקשים מסמך, לא שאלה |
| בכרטיס, לאשר לשנה | עובדה מתמשכת בכרטיס | פריט ברשימת «זה מה שידוע לנו» |
| ממתין לאישור | יש תשובה שלא נבדקה | למשרד; לא שואלים שוב |
| כבר בבקשה פתוחה | פריט זהה נשלח ועוד לא נענה | לא שואלים שוב; תזכורת רק מהמשרד |
| חסר | רלוונטי ואין עליו כלום | מוצע לשאלה |
| לא ידוע אם חל | שאלת הפתיחה של התחום לא נענתה | שואלים רק את שאלת הפתיחה |
| לא חל | לפי תשובה, כרטיס או שנה קודמת | לא מוצג (נגיש תחת «פירוט») |

**זהות פריט** — למניעת כפילות: לקוח + שנה + פריט + אדם + ישות + תקופה.

**אכיפה בשרת:**
- פריט פתוח זהה לא נוצר פעמיים.
- הלחיצה «הוסף לבקשה» אידמפוטנטית.

### 5.2 מדרג

1. **תחום** — שאלת פתיחה אחת. בערך 10 שאלות ללקוח טיפוסי, ופחות אם הכרטיס כבר יודע.
2. **ישות** — רק בתחום שנענה «כן»: «באיזה בנק? של מי?».
3. **סכום או מסמך** — רק כשאין מסמך שעונה עליו. כשיש 106, לא שואלים על משכורת.
4. **מצבים מיוחדים** — רשימת בדיקה למשרד בלבד. ללקוח עובר רק מה שהמשרד סימן.

### 5.3 בקרת כיסוי מאחור

בדף הדוח השנתי יש סעיף מקופל: «כיסוי 1301 לשנה». הוא מציג:
- כמה שדות רלוונטיים יש להם עובדה, לפי חלקי הטופס;
- רשימה של מה שעוד חסר, כדי שהמשרד ישלים.

‼ בקרת הכיסוי לא יוצרת שאלות ללקוח בעצמה. כל שאלה עוברת דרך תחום ופריט מידע.

**בדיקות שנועלות את זה:**
- כל שדה 1301 רלוונטי משויך לפריט מידע;
- לקוח עם הערכה מאושרת לא נשאל שוב על מה שאושר;
- שכיר בלי נכסים ובלי חשבונות מקבל לכל היותר 8 שאלות פתיחה ורשימת מסמכים (תרחיש בדיקה).

## 7. סדר המימוש ובדיקות קבלה

כל אבן דרך עוברת את אותו מסלול: בדיקה עצמאית → מימוש → בדיקות → דפדפן במחשב ובטלפון → תיקון → דוח.
- **מיגרציות:** רק ב-staging עד אישור.
- **ייצור:** אין שינוי נתוני ייצור ואין פריסה בלי אישור מפורש.

| אבן דרך | מה נבנה | בדיקת קבלה עיקרית |
|---|---|---|
| **2.1 קטלוג תחומים ופריטים** | TS: תחומים, פריטי מידע (מה-131 + השדות הממופים), שיוך כל שדה 1301 לפריט | בדיקה: אין שדה 1301 בלי פריט; אין פריט בלי תחום |
| **2.2 מבנה הנתונים** | `tax_year_facts`, `tax_evidence` (מינימלי), RPC כתיבה, אישור ודחייה, allowlist זהה ל-TS | בדיקות SQL: ריק ≠ אפס; תחזית לא מחליפה «בפועל»; `stale_conflict`; תשובה מהדף האישי = `pending` |
| **2.3 תמונת השנה** | פונקציה טהורה (סעיף 5.1) | תרחישים: שכיר יחיד; עצמאי נשוי עם ילדים; זוג עם שכר דירה וחשבון השקעות; מעבר מהערכה לדוח בלי שאלה חוזרת |
| **2.4 סוגי בקשה** | `tax_estimate`, `annual_return` + זהות לפי שנה, תבניות, «עבודת מס» | לחיצה כפולה או שתי לשוניות → בקשה אחת (בדיקת שרת) |
| **2.5 השלמת מידע** | `info_collection`, ענף בדף האישי, שליחה ב«שלח בקשות» | הלקוח עונה → עובדה ממתינה; בן/בת זוג נשמרים כ-`spouse`; פריט פתוח לא נשאל פעמיים |
| **2.6 אישור במשרד** | כרטיס «לאשר תשובות», תיקון במקום והיסטוריה | אישור, תיקון ודחייה נשמרים; התשובה המקורית נשמרת |
| **2.7 מעבר מהקיים** | סכומים שנתיים מהכרטיס → «לאשר שנה»; סשנים קיימים → בקשות; סנכרון השאלון הישן מפסיק לכתוב סכומים שנתיים לכרטיס | ספירה לפני ואחרי ב-staging: אף ערך לא נמחק; ערך לא מאושר לא נכנס לחישוב |
| **2.8 תיק מס › שנות מס** | כרטיסי שנה, עובדות מתמשכות עם מקור | נגיש מהתיק, מבקשות ומעבודת מס; בטלפון «עכשיו» בראש |
