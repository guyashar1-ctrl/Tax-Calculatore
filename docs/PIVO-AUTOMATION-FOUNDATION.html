A foundation for many automations

PIVO needs a reusable path from a client action to a government system and back. The withholding-tax certificate is the first vertical slice, not the design target. What follows is the smallest structure that makes automation #2 and #3 cheap — grounded in what the repository already has, which turns out to be more than half of it.

A

What the repository already gives us

Checked across package.json, src/, scripts/, supabase/ (149 migrations) and docs/. Two findings change the design; one constrains the UI.

The load-bearing discovery

A proposal → human-decision pipeline already exists, and it is the right result channel

tax_fact_changes holds a proposed change to a professional fact: field key, old value, new value, source, and a pending / accepted / rejected status with a decider and a timestamp. propose_tax_facts never writes to clients — every proposal lands as pending, without exception. The accountant accepts or rejects.

This is exactly what an automation should produce. A check that reads a government system is making a claim about a fact; the accountant remains the one who accepts it. Automation results should not get a bespoke surface — they should land here. That single decision is what makes the second and third automation cheap, because their output needs no new UI at all.

It is also already idempotent in the way a retrying worker needs: a partial unique index on (client_id, field_key) WHERE status = 'pending' means re-proposing the same fact refreshes the pending row instead of stacking duplicates.

supabase/90-tax-fact-reconciliation.sql — tax_fact_changes · propose_tax_facts · accept_tax_fact_change · reject_tax_fact_change

The first action's output field already exists as a governed fact

Migration 146 added clients.withholding_status with exactly three values — exempt (פטור), rates (שיעורים לפי פעילות), none (אין אישור תקף) — and wired withholdingStatus into the tax-fact field dispatcher so it can be proposed and accepted like any other fact. The reason given in the migration is that the authority-flags generator must tell "no valid certificate" apart from "rates by activity", because one is fine and the other needs work.

So the first automation has no schema to invent. It reads SHAAM and proposes a value for a column that is already governed, already displayed, and already drives a flag.

What is missing

There is no job queue

Not a table, not a view, nothing. Searched every migration. Every asynchronous thing in the system today is a cron firing an edge function that finishes within its own invocation.

There is no browser automation

No Playwright, no Puppeteer, not even transitively. All 45 Node scripts are plain fetch against the Supabase Management API. A local worker is a from-scratch addition.

The existing claim/release pattern is right in shape and wrong in scope — and it has no lease

claim_auto_execution is a single UPDATE … WHERE payload->>'autoExecutedAt' IS NULL: two concurrent callers, one winner. That is the correct primitive and worth copying. But it is bound to onboarding_steps and claims by writing into a step's payload, so it is a pattern to reuse, not a table.

More important: the claim has no expiry. Release only happens because the caller is an edge function that runs to completion and calls it. A local worker on an office PC can be killed, lose its network, or have the machine sleep — and a claim with no lease leaves that job wedged forever with no retry. The generic model must add a lease; this is the one place where copying the existing pattern verbatim would be a mistake.

The UI constraint you should know about before deciding on the tab

Standing decision in the code

ClientWorkspace.tsx carries an explicit architectural rule, approved 15.07.2026: a new capability enters as a section inside "התיק" or as a letter in the control center — never as a tab. The comment states the reason plainly: a dead tab on every client is exactly what the rule exists to prevent. Two tabs have been added since, and each required a frozen, named design source to override the rule.

Separately, a surface that answers "what needs attention for this client, per authority" already exists: AlignmentStatusView — תמונת מצב מול הרשויות — renders conclusions above the data across ב״ל, מע״מ and מ״ה, driven by computeAuthorityFlags.

You asked for a "בדיקות" tab temporarily, and that word does the work: as a scaffold behind a flag it is a reasonable way to build and see the machinery before deciding where it lands. The recommendation is to make that explicit rather than accidental — ship it as flags.checksTab, defaulting off in production and on for you, so it is a workbench and not a third exception to a rule you wrote for good reasons. Where the results ultimately belong is a product decision (§F), and the strongest candidate is the surface that already exists.

B

Recommended architecture

Three planes. The only new infrastructure is the ledger in the middle and the worker on the right.

PIVO Action button Client tab. Writes one row: action type, client, input.
Supabase Job ledger One table. Status, lease, attempts, result.
Worker Poll & claim Office PC. Narrow edge function, never the DB directly.
Human Authenticate Card, PIN, OTP. Worker detects and waits — never acts.
Module Run action Playwright in the authenticated profile.
PIVO Proposed fact Result lands as a pending tax fact. Accountant accepts.

The four decisions that define it

1. The worker pulls; it is never pushed to. The card is physical, so the worker lives on the office Windows machine, behind no inbound address. This inverts the existing pattern — pg_cron pushes to edge functions today — and it is not optional. The worker polls a narrow endpoint on an interval.

2. The worker never holds a service-role key and never touches the database directly. It authenticates to two edge functions with a dedicated worker secret from Vault: one to claim work, one to report a result. This keeps the blast radius of a compromised office PC to "can claim and complete automation jobs", not "can read every client".

3. Results are proposals, not writes. The worker's structured output becomes a tax_fact_changes row in pending. The accountant accepts. No automation writes a professional fact directly — which is already the rule the codebase enforces for every other source.

4. Actions are modules behind one interface. The worker is a dispatcher: it claims a job, looks up a handler by action_type, and runs it. Adding automation #2 means adding a file that exports one function and registering it. Everything else — claiming, leasing, retrying, reporting, the human-gate handling, the UI — is shared and written once.

What "minimum" means here

One new table, two new edge functions, one new local package, one flag-gated UI surface, and a handler interface. No queue infrastructure, no message broker, no worker registry, no orchestration layer. Polling a table on a 30-second interval is entirely adequate for a workload of a few actions per day.

C

The generic job and action model

One table, seven states, one handler interface. Everything action-specific lives inside two JSON columns.

The ledger

automation_jobs
  id             text primary key
  user_id        uuid        -- owning accountant; drives RLS in PIVO
  client_id      text        -- who this is about
  action_type    text        -- 'shaam.withholding_certificate' — the dispatch key
  input          jsonb       -- action-specific. resolved by PIVO at create time,
                                never re-read from clients by the worker

  status         text        -- see states below
  claimed_by     text        -- worker instance id
  claimed_at     timestamptz
  lease_until    timestamptz -- ‼ the thing the existing pattern lacks
  attempts       int  default 0
  max_attempts   int  default 3

  result         jsonb       -- action-specific structured output
  artifacts      jsonb       -- [{ document_id, kind, filename }] — files land in
                                the existing documents store, not in this row
  error_code     text        -- machine-readable: 'auth_required', 'not_found', …
  error_detail   text        -- human sentence, shown in PIVO
  needs_human    text        -- what the accountant must do, when blocked

  created_at, updated_at, finished_at   timestamptz

  -- one open job per client per action:
  unique (client_id, action_type) where status in
    ('queued','claimed','running','needs_human')

The last line is the idempotency guarantee at the product level: pressing the button twice cannot create two jobs, and the UI can simply show the open one. It also means a retry is the same row, not a new one.

States

queuedPIVO created it. Nobody has touched it.
claimedA worker won the atomic update and holds a lease. If the lease expires, the job returns to queued and attempts stands — this is what makes a killed worker recoverable.
runningThe handler is executing. The worker extends the lease on a heartbeat.
needs_humanThe distinctive state, and the reason this model differs from an ordinary queue. The government system wants a certificate, a PIN, or an OTP. The worker stops, records what is needed, and releases. PIVO shows it. Nothing retries automatically — a human acts, and the job goes back to queued.
succeededStructured result written; any proposed fact is pending the accountant's acceptance.
failedAttempts exhausted, or a non-retryable error. Carries a code and a sentence.
cancelledThe accountant withdrew it.
Retry semantics — say this out loud before building

Only two error classes may be retried automatically: transport failures and lease expiry. An action that reached the government system and got an answer is never retried automatically, even a bad answer — because we cannot generally know whether a submission took effect. For the read-only first slice this is theoretical; the moment an action writes to a government system it is the whole ballgame, so the rule belongs in the foundation now.

The handler interface

// every automation is this, and nothing more
interface AutomationHandler {
  actionType: string;              // 'shaam.withholding_certificate'
  system: 'shaam' | 'btl';         // which session this needs

  // may this run now? cheap, no navigation
  preflight(ctx): Promise<{ ok: true } | { ok: false; needsHuman: string }>;

  // do the thing. throws Retryable / Permanent / NeedsHuman
  run(ctx, input): Promise<{
    result: Record<string, unknown>;
    facts?: { fieldKey: string; label: string; value: unknown }[];
    artifacts?: { path: string; kind: string }[];
  }>;
}

The context carries an authenticated Playwright page, a logger, and a heartbeat callback. It carries no Supabase client — a handler cannot reach the database, so a badly written module cannot corrupt anything. Its only outputs are its return value and its exceptions.

facts is the bridge to §A: whatever a handler returns there is proposed through propose_tax_facts by the reporting endpoint, using the existing machinery.

D

Browser and session lifecycle

The part where the architecture meets a physical smart card.

Placement

A new workspace package in this repo — worker/ — with its own package.json. It shares the repo for versioning and review but not the build: the app must never bundle Playwright, and the worker must never import React. Node, TypeScript, one dependency.

The profile is the session

The worker uses a persistent Chrome profile directory it owns (launchPersistentContext), dedicated to automation and separate from the accountant's daily browser. That directory holds the cookies and the certificate decision; it lives on the office PC and is never uploaded, backed up, or synced. Both of the auth modes you described work against it: the accountant authenticates in that window once, and the worker's later runs reuse it.

Hard boundary

The worker's authentication logic is detection only. It reads the state — tab title HomePage, Error_nocard, a navigation that bounces back, a page call that times out because a native dialog is modal — and maps it to an outcome. It never clicks a certificate dialog, never types a PIN, never touches an OTP field. The detection table for this is already written in the shaam-login skill's screens.md, observed in the field, and it becomes the implementation of one function.

The waiting protocol

  1. Worker claims a job and opens the profile.
  2. preflight checks for a live session. Live → run.
  3. Not live → the worker brings the window forward and leaves it on the login page, sets the job to needs_human with a sentence naming what is needed, and releases the claim. It does not sit in a loop holding the job.
  4. PIVO shows the job as waiting for authentication, with that sentence.
  5. The accountant authenticates in the window that is already open. Nothing to install, nothing to copy.
  6. The next poll finds a live session and the job runs. Whether that requeue is automatic on detecting a live session, or requires the accountant to press "continue", is a product call (§F).

One worker, one browser, one job at a time

Serial execution. A single card, a single session, and a workload of a few jobs a day make concurrency pure cost. The lease and the atomic claim still matter — not for parallelism, but because a second worker will eventually get started by accident, and because a killed worker must not wedge a job.

E

What the first slice actually proves

אישור ניכוי מס במקור — separating what it validates about the reusable system from what it teaches us about one SHAAM screen.

The withholding certificate is a good first slice for reasons that have nothing to do with withholding tax: it is read-only, so a bug cannot submit anything to a government system; its output is a three-value enum that already exists as a governed fact, so it exercises the full result path without inventing schema; and it produces a downloadable certificate, so it exercises the artifact path too.

Proves — about the system

  • A button in PIVO creates a job that a machine outside Supabase picks up.
  • The atomic claim works across processes; a second worker gets nothing.
  • A killed worker's lease expires and the job is picked up again — no wedge.
  • A card-bound session survives between worker invocations.
  • The human gate works end to end: no session → needs_human → accountant authenticates → job completes.
  • A structured result becomes a pending fact the accountant can accept, moving clients.withholding_status through the existing path.
  • A downloaded PDF lands in the documents store, attached to the client.

Does not prove — needs slice 2

  • Anything about writing to a government system, where retry rules bite.
  • That the handler interface fits a second, differently-shaped action — the real test of the abstraction, which is why automation #2 should be chosen deliberately (a BTL action would prove the multi-system assumption).
  • Multi-step actions that span human waits in the middle rather than at the start.
  • Anything about concurrency beyond "one at a time is enough".
Keep these two things apart

The reusable foundation can be built and tested before the SHAAM screens are understood, using a fake handler that returns a fixed answer. That is the recommendation in §H: prove the machinery against a stub, then drop the real handler in. Otherwise a session-lifecycle bug and a page-selector bug arrive on the same afternoon looking identical.

F

Decisions that need you, not me

Five. The first two are genuine data-model commitments; the rest are product calls that change what gets built.

1 · Does automation become a new fact source?

tax_fact_changes.source is a CHECK constraint over exactly four values: questionnaire, manual, institution_alignment, import. Automation output needs a fifth — automation — or it must masquerade as one of these. Adding it is a small migration, but it is a permanent vocabulary change to a governed model, and it affects how provenance reads in the UI for every fact from now on.

Recommendation: add it. A fact whose source was a robot reading a government screen is meaningfully different from one the accountant typed, and the model exists precisely to record that difference.

2 · Where do check results live once the scaffold comes down?

The בדיקות tab is a workbench (§A). The durable answer is either a section inside the existing תמונת מצב מול הרשויות — which already answers "what needs attention, per authority" and would then also carry "and here is what we verified directly" — or a permanent tab, which needs the same kind of frozen design source the other two exceptions required.

Recommendation: build behind flags.checksTab, decide after slice 2, when there are two actions to look at rather than one.

3 · After the accountant authenticates, does the job resume by itself?

Automatic resume is smoother. Explicit resume is honest: the accountant may have logged in for something else entirely, and a job silently starting inside their browser session is surprising. This affects the state machine, so it is worth settling before it is written.

Recommendation: automatic for read-only actions, explicit for anything that writes. Which means the handler declares it — one more field on the interface.

4 · Who owns the worker machine, and what happens when it is off?

A job created on Friday evening sits until the office PC wakes. PIVO should say so rather than showing an indefinite spinner — which means the worker reports a heartbeat, and PIVO surfaces "the worker has not checked in since…". Small, but it is the difference between a system that looks broken and one that looks honest.

5 · How long do job rows and their inputs live?

input will contain client identifiers by necessity. A job ledger is an audit trail worth keeping, but it is also a second copy of identifying data with a different access path than clients. Decide a retention window now — 90 days of finished jobs, say — rather than discovering in a year that the ledger is the largest table of personal data in the system.

G

What still needs one manual capture

The handoff's capture protocol holds — but its unknowns were framed around the representation request. Re-pointed at the withholding certificate, this is the shorter list.

  1. Where the certificate check lives in the portal. Which menu path, and whether it is its own screen or a section of the client query used for representation.
  2. Postback or JSON. Unchanged and still first: it decides whether the handler issues a request or drives a page. Answered in ten seconds with the Fetch/XHR filter.
  3. What the screen actually returns, and how it distinguishes the three states the data model already has — exempt, rates by activity, no valid certificate — plus the validity dates, which the model does not yet carry and may need to.
  4. Whether a certificate PDF is downloadable, and under what filename pattern. This is what exercises the artifact path.
  5. PIN cadence. Once per session, or once per operation. Decides whether unattended runs exist at all.
  6. Session lifetime — how long an idle authenticated session survives. Sets the polling interval and the lease duration.
  7. Whether automated access is permitted under the portal's own נהלים and אבטחת מידע pages. Stop-or-go, and it belongs before the code.

Items 5 and 6 are properties of the session, not of this action — they are answered once and they are inputs to the foundation, which is another reason the capture should happen before milestone 2 rather than during it.

H

Three milestones

Each one ends somewhere you can stop, look at a working thing, and decide whether to continue.

01

The machinery, proven against a stub

The automation_jobs table with its lease and its atomic claim. Two edge functions — claim and report — on the existing secret pattern. The worker/ package with the dispatcher, the lease heartbeat, and one fake handler that sleeps two seconds and returns a fixed answer. The בדיקות tab behind flags.checksTab, with a button, a live status, and an error.

Done when: pressing the button in PIVO changes a row on the office PC and the answer appears back on screen; two workers race and one loses; a worker killed mid-job releases its lease and the next run picks it up.

No SHAAM involved. No browser involved. If this milestone is hard, the problem is the foundation — which is exactly what you want to find out before Playwright is in the room.

02

The session, and the human gate

Playwright with a persistent profile. Session detection implemented from the observed screen signatures. The needs_human path end to end: no session → PIVO says what is needed → the accountant authenticates in the open window → the job completes. Still no real action — the handler navigates to the portal home and reports "session live".

Done when: the gate works from both starting points — an already-authenticated Chrome, and a cold start where the accountant authenticates on request — and a session survives between two worker invocations an hour apart.

Gated on: the manual capture (§G items 5–7) and a yes on Playwright as a dependency.

03

The first real action, on rails already built

The withholding-certificate handler: navigate, read, return a structured result plus a proposed withholdingStatus fact and the certificate PDF as an artifact. The proposal appears in the existing tax-fact review; accepting it moves the client's governed field.

Done when: a real client's status is read from SHAAM and accepted into PIVO without anyone opening the portal by hand — and the diff for this milestone is one handler file plus its registration, which is the actual proof that automation #2 is cheap.

Gated on: the manual capture (§G items 1–4).

Sequencing note

Milestone 1 needs nothing from you but a yes. It touches no government system, adds no browser dependency, and is the half of the architecture most likely to be wrong in a way that is expensive later. It can start while the capture is still unscheduled.
