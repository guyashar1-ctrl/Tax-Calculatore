2. **שתי כתובות לאותו נתון, והביצוע קורא את הלא-נכונה.** מסך «נתונים לביצוע
   הייצוג» (`RepresentationAuthorityData.tsx:213-220`) קורא את ארבעת שדות בן/בת
   הזוג מ-`request.identification` ⇒ `request.prefill` ⇒ פיצול `spouseName`, **ולא
   מהכרטיס**. אצל דין הכרטיס מחזיק ת.ז. ושם — והמסך מציג ריק. מיגרציה 149

   ביסודות («היטל אינו מקור אמת»).

## 2 · מודל המוצר — «תנאי-קדם» כמושג מפורש

### 2.1 הגדרה

**תנאי-קדם של בקשה** = מידע קנוני (שדות בכרטיס) שבלעדיו לא ניתן לבצע את
הצעד הבא של הבקשה. תנאי-קדם **אינו בקשה** (אין לו «למצוא / להמשיך /
היסטוריה» משלו — הוא נעלם ברגע שהמידע קיים, ולא משנה מי סיפק אותו). הוא
**מצב נגזר** של הבקשה: `missing = required − present`.

### 2.2 שלושת המודלים שנשקלו

| קריטריון | א · קידוד בכל סוג בקשה (`if authority_representation && spouse …` בכרטיס) | **ב · הגדרות דרישה לשימוש חוזר + מצב נגזר לבקשה** | ג · בן «איסוף פרטים» כבקשה משלו |
|---|---|---|---|
| בהירות מחזור | חלשה: כל כרטיס ממציא נוסח ו-gating משלו | **גבוהה**: מצב אחד «נדרשים פרטים» עם משמעות זהה בכל סוג | טובה מקומית, אבל שני מחזורים על עבודה אחת |
| UX ב«בקשות» | שקט אבל לא עקבי | **שקט ועקבי**: שורת מצב + פעולה ראשית אחת | **פיצוץ בקשות**: כל ייצוג מוליד «פרטים» שנפרד ממנו |
| בעלות על נתונים | מפוזרת | **אחת**: הדרישה מצביעה על שדות קנוניים | פיתוי לאחסן ב-`payload` של הבן (צל) |
| ביקורת | לפי מימוש | **אחידה**: אירוע `prerequisites_filled` על הבקשה + `tax_fact_changes` | מפוצלת בין הורה ובן |
| אידמפוטנטיות | לא רלוונטי | **טבעית**: המצב נגזר, כתיבה חוזרת = no-op | צריך ייחודיות לבן |
| אבטחה | — | **קישור-לשלב עם רשימת שדות מפורשת** | קישור לבן — שקול |
| זהות משתתף | — | **מטא-נתון על הקישור/האירוע** | מתפתה להפוך לבעלים של הבן |
| הרחבה מעבר לב"ל | העתקה | **הוספת שורה למרשם הדרישות** | סוג שלב לכל דרישה |
| מיגרציה | קלה | **בינונית**: מרשם + עמודת קישורים + סנכרון | כבדה: סוג שלב, אינדקסים, קינון |
| כפילות | — | נמוכה | גבוהה (בן לכל ניסיון) |

**הכרעה: מודל ב.** דרישה מוגדרת פעם אחת (מרשם), המצב לבקשה נגזר בשרת
מהכרטיס, ואיסוף מהמשתתף הוא **קישור** (לא בקשה). ג' נדחה במפורש — «תנאי-קדם
אינו אוטומטית בקשה נוספת»; א' נדחה כי הוא בדיוק מה שהוליד את 0.2.

### 2.3 המרשם — מה נדרש, לאיזה שלב, ממי

מרשם אחד, **בשרת** (פונקציית SQL `requirements_for_step(step)`), כדי שגם
הסנכרון וגם הדף הציבורי וגם הכרטיס יקראו אותה רשימה. הדפדפן מקבל את התוצאה
דרך `payload.prerequisites` (היטל שהטריגר כותב) ואינו מחשב בעצמו.

```
requirement set = {
  key:        'btl.entry'                       -- מזהה הסט
  stage:      'entry' | 'instructions'          -- לאיזה צעד בבקשה
  subject:    'client' | 'spouse'               -- על מי (נגזר מ-payload.subjectRole)
  fields:     [ { key, kind, label, validate } ]-- מפתחות Client קנוניים
}
```

| סוג בקשה × תנאי | סט | שדות (מפתחות `Client`) | קיים היום ב-`Client`? |
|---|---|---|---|
| `authority_representation` · `national_insurance` · `subjectRole=spouse` · שלב `entry` | `btl.entry/spouse` | `spouseFirstName`, `spouseLastName`, `spouseIdNumber` (Luhn), `spouseBirthYear` (4 ספרות, 1900–שנה) | כן (110) |
| … · `subjectRole=client` · `entry` | `btl.entry/client` | `firstName`, `lastName`, `idNumber`, `birthDate` (השנה נגזרת) | כן |
| … · שלב `instructions` (מצב 3 ⇒ 4) | `btl.instructions/<role>` | `spouseEmail` / `email` | כן (113) — כבר מטופל ב-`NiInstructionsDialog`; נכנס למרשם רק כדי שהכרטיס יאמר «חסרה כתובת» **לפני** הלחיצה |

מה **לא** נכנס למרשם במיילסטון הזה (מתועד ב-§10): מע״מ/ניכויים לאדם, בנק,
מסמכים, חתימות. המרשם נבנה כך שהוספת שורה היא הוספת סט, לא קוד חדש.

### 2.4 המצב הנגזר על הבקשה

`payload.prerequisites` (נכתב **רק** ע"י `sync_authority_representation_steps`, לעולם
לא מהדפדפן):

```json
{ "stage": "entry",
  "required": ["spouseFirstName","spouseLastName","spouseIdNumber","spouseBirthYear"],
  "missing":  ["spouseBirthYear"],
  "satisfiedAt": null,
  "link": { "id": "…", "sentAt": "…", "expiresAt": "…", "submittedAt": null } }
```

- `missing` ריק ⇒ `satisfiedAt` נחתם (פעם אחת; לא מתאפס אם שדה נמחק אחר כך —
  זה שינוי מצב מקצועי, לא פתיחת תנאי-קדם מחדש; דגל «דורש טיפול» יטפל).
- `link` הוא היטל של `request_participant_links` (§4) לנוחות הכרטיס.

## 3 · בעלים / נושא / משתתף

| מושג | מהו | היכן נשמר | האם ישות בדומיין? |
|---|---|---|---|
| **בעלים** | הכרטיס שהבקשה שייכת לו | `onboarding_steps.client_id` | כן (קיים) |
| **נושא** | על מי העבודה | `payload.subjectRole` (+ `subjectName` צילום) | כן (קיים) |
| **משתתף / ספק** | מי מתבקש/ת עכשיו לספק מידע או לפעול | `request_participant_links.participant_role`; `onboarding_events.actor` + `meta.actorRole` | **לא** — מטא-נתון של אינטראקציה |

**הכרעה: אין זהות שלישית בדומיין.** נימוקים ודוגמאות:

- ברירת המחדל: משתתף = נושא (דין ממלאת את פרטי דין). המשרד ממלא ⇒ משתתף =
  `office`. הבעלים ממלא על הנושא (גיא מקליד את שנת הלידה של דין) ⇒ משתתף =
  `owner`. רו"ח קודם מעלה חומרים ⇒ משתתף = `externalParty` (כבר קיים כך).
- בכל המקרים **הנתון נכתב לאותו מקום** ומה שמשתנה הוא רק «מי סיפק» — כלומר
  ביקורת. ישות דומיין למשתתף הייתה מוסיפה בעלים-בפועל שני לבקשה, בניגוד ל-§5
  ביסודות.
- אם בעתיד יהיה לנושא כרטיס/טוקן משלו (150) — הוא הופך לבעלים של הבקשות
  שלו (יסודות §15), לא ל«משתתף».

## 4 · מודל הנתונים

### 4.1 קישורי משתתף — טבלה חדשה (מוצדקת: תפוגה, ביטול, ייחודיות, ביקורת)

```sql
create table public.request_participant_links (
  id                 text primary key default replace(gen_random_uuid()::text,'-',''),
  user_id            uuid not null,                    -- המשרד
  step_id            text not null references onboarding_steps(id) on delete cascade,
  client_id          text not null,                    -- הבעלים (דנורמליזציה לבדיקות)
  participant_role   text not null check (participant_role in ('client','spouse')),
  requirement_key    text not null,                    -- 'btl.entry'
  field_keys         text[] not null,                  -- מה מותר לכתוב, נעול ביצירה
  token              text not null unique,             -- 32 hex, gen_random_bytes(16)
  expires_at         timestamptz not null,             -- now() + 14 days
  sent_to            text,                             -- הכתובת שנפתרה בשרת (ביקורת בלבד)
  sent_at            timestamptz,
  opened_at          timestamptz,
  submitted_at       timestamptz,
  revoked_at         timestamptz,
  created_at         timestamptz not null default now()
);
create unique index request_participant_links_active_idx
  on request_participant_links (step_id)
  where submitted_at is null and revoked_at is null;   -- קישור פעיל אחד לשלב
```

למה לא `payload.participantToken` כמו `releaseToken`: תפוגה/ביטול/היסטוריה של
כמה קישורים לאותו שלב, ואינדקס ייחודיות — לא נכנסים בנוחות ל-jsonb. הטבלה
**אינה** מחזיקה נתונים שהמשתתף מילא — רק את הקישור.

### 4.2 שינויים ב-`onboarding_steps`

אין עמודות חדשות. `payload.prerequisites` (§2.4). אין סוג שלב חדש.

### 4.3 `email_messages`

ללא שינוי. שורה חדשה עם `step_id`, `kind='participant_details'`,
`meta:{participantRole, linkId}`.

### 4.4 `onboarding_events` — אירועים חדשים

| `type` | `actor` | `meta` |
|---|---|---|
| `prerequisites_missing` (בסנכרון, כשהרשימה משתנה) | `system` | `{stage, missing}` |
| `participant_link_created` | `accountant` | `{linkId, participantRole, fieldKeys, expiresAt}` |
| `participant_link_sent` / `_revoked` / `_expired` | `accountant`/`system` | `{linkId}` |
| `prerequisites_filled` | `accountant` \| `participant` \| `client` | `{linkId?, participantRole, fields:[…], via:'office'\|'link'\|'portal'}` |
| `prerequisites_satisfied` | `system` | `{stage}` |

### 4.5 בעלות קנונית — הכלל

**המקום היחיד שנכתב הוא הכרטיס** (`clients.<column>`), לפי מפתחות ה-`Client`.
`representation_requests.identification.spouse*` ו-`prefill` הופכים ל**היטל
היסטורי** (מה הלקוח הגיש בקליטה) ואינם נקראים יותר לצורך ביצוע:
`RepresentationAuthorityData` קורא **קודם מהכרטיס** ורק אם ריק — מהם
(תיקון 0.2). אין כתיבה אליהם מהפרימיטיב החדש.

## 5 · מודל הכתיבה הקנונית — נקודת ההתכנסות

פונקציה פנימית אחת (SECURITY DEFINER, לא חשופה):

```
apply_request_prerequisites(p_step_id, p_values jsonb, p_actor text, p_link_id text)
```

1. טוען את השלב, את הכרטיס (`for update`), ואת `requirements_for_step(step)`.
2. **רשימת היתר**: כל מפתח ב-`p_values` חייב להיות ב-`fields` של הסט (ולקישור —
   ב-`field_keys` של הקישור). מפתח זר ⇒ `{ok:false, reason:'field_not_allowed'}`,
   אפס כתיבות.
3. **ולידציה בשרת** לפי `kind` (Luhn לת.ז.; שנה 1900–שנה נוכחית; מייל; טלפון) —
   אותן פונקציות שמשמשות את `validate_requirements`/`portal_submit_step`.
4. **כתיבה**: לכל מפתח — אם הוא במרשם העובדות המנוהלות (`_tax_fact_field_op`)
   ⇒ `record_manual_fact_change`-שקול פנימי (אותה שורת `tax_fact_changes`, `source =
   'prerequisite'`, `actor`); אחרת `update clients set <col>` + שורת
   `tax_fact_changes` שוות-ערך (`source='prerequisite'`) — כדי שלכל שדה יש
   היסטוריה, גם לשדות שאינם «מנוהלים» היום. **ערך זהה ⇒ אפס כתיבה** (אידמפוטנטי).
5. `log_onboarding_event('prerequisites_filled', p_actor, …)`.
6. הטריגר על `clients` (157) מריץ סנכרון ⇒ `missing` מתעדכן ⇒ אם ריק:
   `satisfiedAt`, אירוע `prerequisites_satisfied`, **וביטול אוטומטי** של קישור
   פעיל (`revoked_at = now()`, אירוע `participant_link_revoked{reason:'satisfied'}`).

שני ה-RPC החשופים קוראים **רק** לה:

| RPC | מי | תיחום |
|---|---|---|
| `complete_request_prerequisites(p_step_id, p_values)` | `authenticated`; `auth.uid() = step.user_id` | `actor='accountant'` |
| `participant_submit_prerequisites(p_token, p_values)` | `anon` (ברשימת ההיתר של 160) | טוקן ⇒ קישור פעיל ולא פג ⇒ `actor='participant'`, `field_keys` של הקישור |

## 6 · מעברי מצב של הבקשה (הרחבת טבלת 157 §2.4)

הסנכרון מחשב קודם תנאי-קדם, ורק אז את ראיות הביצוע:

| # | ראיה | `status` | `ball` | משפט המצב | פעולה ראשית |
|---|---|---|---|---|---|
| 0a | `missing(entry) ≠ ∅` ∧ אין קישור פעיל ∧ ¬`enteredAt` | `pending` | me | «נדרשים פרטים מ{subjectName} כדי להמשיך» | «מלא פרטים עכשיו» + «שלח ל{שם} להשלמת פרטים» |
| 0b | `missing(entry) ≠ ∅` ∧ קישור פעיל | `waiting_client` | client | «נשלח ל{שם} להשלמת פרטים · {sentAt}» | «מלא פרטים עכשיו» (משני: «שלח שוב», «בטל קישור») |
| 0c | `missing(entry) ≠ ∅` ∧ קישור **פג** | `pending` | me | «הקישור ל{שם} פג — לא הושלמו פרטים» | כמו 0a |
| 1 | מסלול ריק ∧ `missing(entry) = ∅` | `pending` | me | «נדרשת הזנה בפורטל ב״ל» | «למרכז הייצוג ←» |
| 2 | `enteredAt` | `in_progress` | me | «הייצוג הוזן · ממתינים לאסמכתא» | — |
| 3 | `referenceNumber` ∧ ¬`instructionsSentAt` ∧ `missing(instructions)=∅` | `in_progress` | me | «אסמכתא … · נדרש לשלוח הוראות אישור» | «שלח הוראות אישור» |
| 3′ | כמו 3 ∧ `missing(instructions) ≠ ∅` | `in_progress` | me | «אסמכתא … · חסרה כתובת מייל ל{שם}» | «שלח הוראות אישור» (הדיאלוג אוסף כתובת — קיים) |
| 4 | `instructionsSentAt` | `waiting_client` | client | «נשלח … ממתינים לאישור» | «שלח שוב» |
| 5 | `confirmedAt` ∨ `tax_files=active` | `completed` | — | «ייצוג פעיל» | — |

- `enteredAt` קיים ⇒ תנאי-הקדם של `entry` אינם נבדקים יותר (הראיה גוברת: אם הוזן,
  הוזן). זה שומר על ההיסטוריה של מי שכבר עבר.
- `waiting_client` משמש כבר ל-4; ההבחנה בכרטיס היא לפי `payload.prerequisites.link`
  (0b) מול `instructionsSentAt` (4). המונים ב«בקשות» («אצל הלקוח») נכונים בשניהם.
- קישור פעיל **אינו** מונע «מלא פרטים עכשיו» — ההתכנסות היא בשדות, לא בנתיב.

## 7 · שתי הזרימות — ומה משותף

### 7.1 «מלא פרטים עכשיו» (משרד)

- **איפה**: בתוך כרטיס הבקשה ב«בקשות», גילוי הדרגתי (§8, כיוון א׳). אותו טופס
  זמין גם מ«דורש טיפול» בתיק המס דרך אותה בקשה (ניווט לשלב, לא טופס שני).
- **שדות**: `required` של הסט; שדות שכבר קיימים מוצגים ממולאים וניתנים לעריכה;
  החסרים מסומנים. אין שדות מעבר לסט (לא «בזמן שאתה כאן…»).
- **כתיבה**: `complete_request_prerequisites(stepId, {spouseBirthYear: 1998})`.
- **ביקורת**: `tax_fact_changes` (`source='prerequisite'`, `actor` המשרד) +
  `prerequisites_filled{via:'office'}`.
- **אחרי**: הטריגר מסנכרן; הכרטיס עובר ל-1 «נדרשת הזנה בפורטל» באותו רינדור
  (הדפדפן קורא מחדש שלבים + כרטיס — אותו `refresh` שכבר קיים אחרי `onSent`).

### 7.2 «שלח ל{שם} להשלמת פרטים» (משתתף)

1. **כתובת**: הנמען נפתר בשרת מהכרטיס (`spouse_email` / `email`). חסרה ⇒ הדיאלוג
   מבקש/מעדכן את הכתובת הקנונית **לפני** יצירת הקישור (אותו `NiInstructionsDialog`-דפוס:
   `EmailInput` ⇒ `onUpdateClientFields`). **חלופה ללא מייל**: «העתק קישור» —
   הבעלים מעביר בעצמו (כמו `spousefill`); אז `sent_to = null`, `sent_at = null`,
   ואירוע `participant_link_created` בלבד.
2. **יצירה**: `create_participant_link(p_step_id)` (authenticated) ⇒ מבטל קישור פעיל
   קודם (אם יש) ⇒ יוצר חדש עם `field_keys = missing ∪ required` (המשתתף רשאי לתקן
   גם שדה שכבר מולא לגביו — זה הנתון שלו), `expires_at = now()+14d`.
3. **מייל**: `send-step-email` עם `kind='participant_details'` ⇒ תצוגה מקדימה ב-
   `EmailPreviewDialog` ⇒ שליחה ⇒ `email_messages(step_id, kind, meta:{linkId})`
   ⇒ `sent_at/sent_to` על הקישור. הנוסח: «{שם משרד}: {ownerFirst} ביקש/ה
   ייצוג עבורך בביטוח לאומי. כדי להמשיך נדרשים {N} פרטים — קישור אישי, תקף
   ל-14 יום.» CTA ⇒ `?participant=<token>`.
4. **מה המשתתף רואה** (`get_participant_form(p_token)` — anon): מיתוג המשרד
   (PIVO + שם הרו"ח — `pivo-brand-split`), שם הבעלים (פרטי), שמו/ה, **רק** את
   שדות הסט עם הערכים הנוכחיים שלו/ה (למילוי/אישור), והסבר של משפט אחד למה.
   **לא** רואה: שום שדה אחר של הכרטיס, בקשות אחרות, מספרי תיק, הכנסות.
5. **המשך/חזרה**: הקישור נפתח שוב עד `submitted_at` או תפוגה; `opened_at`
   נרשם בפתיחה הראשונה. אחרי הגשה ⇒ «תודה, הפרטים נקלטו» (אין עריכה חוזרת;
   תיקון = קישור חדש מהמשרד).
6. **הגשה**: `participant_submit_prerequisites(token, values)` ⇒ §5 ⇒
   `submitted_at` ⇒ הקישור נסגר ⇒ אירוע ⇒ הסנכרון מזיז את הכרטיס ל-1.
7. **מה המשרד רואה**: שורת מצב על הכרטיס: «נשלח לדין · 12.9 · נפתח 13.9 · טרם
   הוגש» / «הוגש 14.9 ✓» + `EmailStatusRow` (נמסר/נפתח) — **בלי** לוג. אין
   התראה נוספת במיילסטון הזה (`queue_accountant_notification` — הרחבה מתועדת).

### 7.3 ההתכנסות (הכלל)

- שני הנתיבים ⇒ `apply_request_prerequisites` ⇒ **אותן עמודות** ⇒ אותו טריגר ⇒
  אותו מצב 1. אין עותק ב-`payload`, אין עותק בקישור, אין עותק ב-`identification`.
- **מקביליות**: המשרד מילא בזמן שקישור פעיל ⇒ `missing` התרוקן ⇒ הקישור בוטל
  אוטומטית; המשתתף שפותח/ת אותו רואה «הפרטים כבר הושלמו — תודה» (`already_satisfied`),
  אפס כתיבות. המשתתף הגיש/ה כשהמשרד עדיין עורך ⇒ הכתיבה האחרונה נשמרת,
  **שתיהן** בהיסטוריה (`tax_fact_changes`); דגל בכרטיס אם הערכים שונים
  («דין הזינה 1998, המשרד 1997 — לבדוק»). הגשה על קישור שפג/בוטל ⇒ `link_expired`,
  אפס כתיבות.
- **הבעלים דרך הדף האישי** (גיא ממלא על דין): לא במיילסטון הזה. מתוכנן כפריט
  `action` בדף עם `actionKind='prerequisites'` ⇒ אותו `apply_…` עם `actor='client'`.
  נדחה כדי שהמיילסטון ישאר בגודל אחד; המודל כבר תומך.

## 8 · UX — שלושה כיוונים, והמלצה

המשותף לכולם: **הכרטיס נשאר רגוע** — שורת מצב אחת, סיבה אחת, החלטה ראשית
אחת; השדות עצמם לעולם לא בכותרת הכרטיס.

### כיוון א׳ · «שורת שער + גילוי הדרגתי בתוך הכרטיס» — **מומלץ**
```
ייצוג בביטוח לאומי — דין וולוצקי ישר        ממתין · הכדור אצלי
נדרשים פרטים מדין כדי להמשיך (חסר: שנת לידה)
[מלא פרטים עכשיו]   [שלח לדין להשלמת פרטים]
   ▼ (אחרי «מלא פרטים עכשיו» — נפתח באותו כרטיס)
   שם פרטי  [דין]   שם משפחה [וולוצקי ישר]   ת.ז. [209422500]   שנת לידה [____]
   [שמור]  [ביטול]
```
- מבנה: הכרטיס הקיים (`AuthorityRepresentationStepCard`) + בלוק תנאי-קדם
  שמופיע רק במצבים 0a–0c; הטופס נפתח **במקום** שני הכפתורים.
- קישור פעיל: השורה הופכת ל«נשלח לדין · 12.9 · טרם הוגש» + [מלא פרטים עכשיו]
  ראשי, [שלח שוב]/[בטל] משניים.
- יתרונות: אפס ניווט, זהה בדסקטופ ובמובייל (הטופס נערם אנכית), עקבי עם
  «מה אני צריך מהלקוח» שמקנן תוכן בתוך הכרטיס. חיסרון: כרטיס ארוך זמנית.

### כיוון ב׳ · «ציר-שלבים בראש הכרטיס + מגירה תחתונה»
```
● פרטים  ○ הזנה בפורטל  ○ אסמכתא  ○ הוראות  ○ אישור
נדרשים פרטים מדין                                  [להשלמת פרטים ▸]
```
- הפעולה פותחת מגירה (bottom sheet) עם שני לשוניות: «מלא עכשיו» / «שלח לדין».
- יתרונות: המחזור כולו נראה במבט. חסרונות: ציר-שלבים הוא רכיב חדש שאינו קיים
  בשום כרטיס אחר (סותר את «כרטיס אחיד» של `JourneyRow`); הכפתור הראשי הופך
  להחלטה מושהית (שני קליקים); ההחלטה «מי ממלא» נדחקת ללשונית.

### כיוון ג׳ · «כרטיס מינימלי + חלונית צד/מודל ייעודי»
```
ייצוג בביטוח לאומי — דין וולוצקי ישר
נדרשים פרטים מדין                                    [השלמת פרטים]
```
- מודל בגובה מלא: כותרת «פרטים לייצוג ב"ל — דין», שני מצבים (מלא / שלח),
  הטופס, מצב הקישור, היסטוריה של הכתיבות.
- יתרונות: הכרטיס הכי שקט; מקום להיסטוריה. חסרונות: ההחלטה הראשית (מי ממלא)
  נעלמת מהכרטיס; מודל נוסף על מודל (התצוגה המקדימה של המייל היא כבר מודל);
  במובייל — מודל בתוך מודל.

**המלצה: א׳.** הוא היחיד שבו שתי ההחלטות גלויות בכרטיס בלי ניווט, שמשתמש
ברכיבים קיימים בלבד (`StepCardShell`, `EditControl`/`EmailInput`, `EmailPreviewDialog`),

## 9 · נתונים קיימים ומילוי-לאחור (מיגרציה `165-request-prerequisites.sql`)

1. **סט הדרישות** (`requirements_for_step`) + הרחבת `sync_authority_representation_steps`
   (§6) + טבלת הקישורים + שלושת ה-RPC + הרשאות (`revoke … from public, anon` לכולן
   מלבד שני ה-anon; 160 מכסה ברירת מחדל).
2. **סנכרון מחדש** של כל `authority_representation` פתוח ⇒ `payload.prerequisites`
   נכתב לכולם. **אין** יצירת קישורים, **אין** מיילים, **אין** שינוי שדות בכרטיס.
3. **השלמה חד-פעמית של צל ⇒ קנוני** (כלל 113 — «כתובת שנמסרה פעם אחת לא תיקבר
   בבקשת ייצוג ישנה»): לכל כרטיס עם `spouse_email` ריק ו-`signers[role='spouse'].email`
   קיים ⇒ העתקה לכרטיס + `tax_fact_changes(source='backfill_165')`. וכן
   `identification.spouseFirstName/LastName/IdNumber/BirthYear` ⇒ עמודות ריקות
   בלבד (149 כבר עושה זאת קדימה). **מכריע לאישור** (§12): זו כתיבה לנתוני אמת,
   מכללה שכבר קיימת במוצר, ומתועדת אירוע-אירוע.
4. **גיא/דין, אוטומטית ובלי מגע ידני**: אחרי 2 — הבקשה של דין: `required =
   [4 שדות]`, `missing = ['spouseBirthYear']` ⇒ הכרטיס: «נדרשים פרטים מדין כדי
   להמשיך (חסר: שנת לידה)» + שני הכפתורים. אחרי 3 — `spouse_email = din@…`
   ⇒ «שלח לדין» זמין מיד בלי לבקש כתובת. הבקשה של גיא (`completed`) — ללא שינוי
   (`enteredAt` ⇒ תנאי-קדם לא נבדקים). **שום דבר לא נוגע ב-`representation_requests`.**
5. `domain_consistency_report()`: שלב עם `enteredAt` ו-`missing≠∅` (לא אמור
   לקרות); קישור פעיל לשלב סגור; `spouse_email` ריק עם חותם-בן/בת-זוג.
